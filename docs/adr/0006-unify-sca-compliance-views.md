# ADR-0006: Unify SCA Compliance Views

> We centralize SCA compliance evaluation in the gateway and expose a read model in OpenSearch for the web dashboard, instead of keeping the only corporate compliance view in the desktop client.

## Context

We have two separate views of Security Configuration Assessment (SCA) results:

1. **Agent Status Desktop Client** shows a curated corporate compliance view with aggregated scores, custom categories, mandatory flags, and remediation instructions. It is only accessible to users with the desktop application installed.
2. **Wazuh Dashboard** (web, deployed via Helm) exposes native SCA results without corporate compliance enrichment. It shows raw check results per agent per policy, but lacks aggregated compliance scoring, mandatory flag visibility, and business-aligned category groupings.

SOC analysts need a centralized compliance view accessible from the web dashboard: to see compliance posture across all agents, filter by non-compliant agents, and understand which corporate security requirements are not met. The current split forces cross-referencing between two systems, and the corporate compliance score is only visible on the desktop client.

The `wazuh-gateway` fetches raw SCA results from the Wazuh Manager API and evaluates them against corporate compliance profiles (`linux.json`, `macos.json`, `windows.json`). These profiles are a curated subset of Wazuh's full SCA checks. The gateway already contains the compliance evaluation logic, but it is consumed by a single client; no other system can access the corporate compliance view.

The deciding forces were: keep a single compliance evaluation engine, let SOC teams consume compliance information without desktop client access, preserve compatibility with existing Wazuh SCA capabilities, minimize additional operational components, and support future compliance consumers (API integrations, reports, SIEM, ticketing systems).

## Decision

The `wazuh-gateway` becomes the compliance evaluation and aggregation layer between Wazuh native SCA data and compliance consumers. Compliance evaluation and business rule interpretation belong to the gateway domain layer, not to individual consumers. The gateway produces a **Compliance Model**, the normalized domain representation containing compliance scores, statuses, categories, mandatory requirements, remediation information, and metadata required by downstream consumers. OpenSearch serves as a compliance read model optimized for dashboard queries; the Gateway API serves desktop and programmatic consumers.

The authoritative inputs are Wazuh SCA results and corporate compliance profiles. The Compliance Model generated by the gateway is the canonical representation of evaluated compliance posture. OpenSearch is a projection, not the source of truth.

Concretely:

- The gateway exposes `POST /compliance/sync` (used by a scheduled CronJob and a dashboard refresh button) and `GET /compliance/sync-status/{sync_id}`.
- Only one synchronization job runs at a time; concurrent requests reuse the existing sync and return `already_running`.
- The gateway indexes two document types into OpenSearch: check-level documents (one per check per agent, for drill-down) and summary documents (one per agent, for fleet-level queries).
- Incremental sync skips agents whose compliance score, passed count, failed count, profile version, and profile content hash are unchanged since the last sync.
- Documents use deterministic IDs for idempotent re-indexing.

The detailed technical design, including document schemas, index mapping, and sync state management, is in the companion document [Compliance Read Model Design](../compliance-read-model-design.md).

## Options considered

| Option                                                         | Verdict  | Why (one line)                                                                                           |
| :------------------------------------------------------------- | :------- | :------------------------------------------------------------------------------------------------------- |
| Keep compliance only in the desktop client                     | Rejected | SOC users require web-based access without installing the desktop client.                                |
| Implement compliance logic inside OpenSearch dashboards        | Rejected | Business rules would be duplicated in visualization tooling, creating maintenance burden.                |
| Create a dedicated compliance service                          | Rejected | Duplicates deployment and operations at current scale; the evaluator stays extractable from the gateway. |
| Centralize evaluation in the gateway and project to OpenSearch | Adopted  | One evaluation engine, one source of truth, minimal new infrastructure.                                  |

## Consequences

**Not part of this decision:** replacing Wazuh native SCA functionality, modifying Wazuh SCA policy files, building a new compliance evaluation engine, creating a new authentication mechanism for compliance data, and providing real-time compliance monitoring (periodic sync is sufficient).

### Impact

**Benefits**

- A single compliance evaluation engine provides consistent results across all user interfaces.
- Corporate compliance profiles are maintained in one place and consumed by all consumers.
- SOC analysts access compliance data via the web dashboard without requiring desktop client installation.
- Future consumers (API, reports, SIEM, ticketing) can be added without modifying the evaluation engine.
- Minimal operational overhead: the change extends an existing service rather than introducing new components.

**Costs**

- The gateway now handles API traffic, compliance evaluation, batch synchronization, and OpenSearch indexing. The compliance synchronization workflow stays isolated behind a dedicated module boundary (`wazuh-gateway/src/compliance/`) so extraction into a separate worker remains possible.
- Compliance data is as fresh as the last sync cycle; an on-demand refresh mechanism covers time-sensitive scenarios.

**Risks**

- If the gateway is down, the compliance index stops updating. Native SCA data in `wazuh-alerts-*` remains unaffected, and the dashboard's native SCA module continues to work.
- Indexing is idempotent; a next successful cycle overwrites stale data.
- The Wazuh Manager API rate limits are handled with controlled concurrency and exponential backoff.

### Accepted limits

- The model provides current compliance posture only; historical trend analysis requires an additional retention strategy.
- Each agent x check generates a document; this is minimal for typical fleet sizes.
- A gateway restart loses in-memory sync state and triggers a full re-sync (safe default).

### Done when

- [x] The gateway exposes `POST /compliance/sync` and `GET /compliance/sync-status/{sync_id}`.
- [x] The gateway evaluates SCA results against corporate compliance profiles.
- [x] The gateway indexes check-level and summary documents into `wazuh-custom-compliance-*`.
- [x] Incremental sync skips unchanged agents using score, counts, profile version, and content hash.
- [x] Only one sync runs at a time; concurrent requests receive `already_running`.

### Revisit when

- The compliance synchronization duration or Wazuh API load grows enough to justify extracting the synchronizer into a dedicated worker.
- A compliance history or trend-analysis requirement appears.
- The project starts building container images or binaries that should be covered by compliance scanning.

## Rollback

**Nothing to roll back.** The gateway API additions are additive: existing desktop clients continue using the gateway API directly, and no breaking changes are introduced to the existing gateway API during the migration. Disabling the OpenSearch projection leaves native SCA data and the existing gateway API unaffected.
